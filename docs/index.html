Guide du développeur · projet ARLA, EPITA SIGL

Expense.io, de l'architecture au premier commit

Expense.io est un SaaS B2B de notes de frais, multi-tenant : un tenant est une entreprise. Un employé soumet une note avec son reçu, son manager la valide ou la rejette, et la RH tranche celles des managers qui n'ont pas de manager. Cette page montre comment le projet est construit, pourquoi il l'est ainsi, et comment y contribuer sans rien casser.

1dépôt, un monolithe modulaire
2processus : web et worker, le même code
3services : PostgreSQL, S3, SMTP
0broker : la file est une table PostgreSQL
  • Next.js 16 (App Router)
  • React 19
  • TypeScript strict
  • Tailwind 4
  • Auth.js v5
  • PostgreSQL 16, SQL brut, RLS
  • S3 (LocalStack)
  • SMTP (Mailpit)
  • Tesseract.js
  • Vitest
  • Playwright
La règle d'or Ne jamais casser le comportement existant : les tests E2E sont rejoués par les correcteurs. Un test E2E rouge est une régression, on corrige le code, pas le test. Un comportement ne change que si une ADR acceptée le décide (ADR-005 §2).

Le métier

Le produit#

Trois rôles, une chaîne de validation, une note qui ne se tranche qu'une fois.

🧾

Employé · employee

Soumet ses notes avec un reçu (PNG, JPEG, WebP, PDF, 10 Mio au plus), voit les siennes et peut préremplir montant, date et description depuis le reçu.

✅

Manager · manager

Valide ou rejette les notes de ses subordonnés directs. Le rôle ne s'attribue que par le seed ou en base.

🏢

RH · hr_admin

Invite les salariés, rattache chacun à un manager de l'entreprise et tranche les notes des managers racines, qui n'ont pas de manager.

Règles à connaître

  • Une décision par note. La seconde reçoit 409 ALREADY_DECIDED et n'envoie aucun email. Chaque note garde qui l'a tranchée et quand (decided_by, decided_at), sans changer les réponses JSON.
  • Invisible vaut inconnu. Une note d'une autre entreprise ou d'une autre équipe donne 404, exactement comme une note qui n'existe pas.
  • Emails. À la soumission, l'approbateur est prévenu : le manager direct, ou toutes les RH de l'entreprise pour un manager racine. À la décision, le soumetteur est prévenu. Contenu minimal : description, statut, lien ; ni montant ni reçu.
  • Sans approbateur. Un employé sans manager peut soumettre, mais personne ne peut trancher sa note et aucun email ne part.
  • Inscription. Le domaine de l'email ne donne aucun droit : s'inscrire sans invitation crée sa propre entreprise, dont on devient RH ; rejoindre une entreprise passe par une invitation de sa RH (détail).

Vue d'ensemble : services et processus#

Un seul dépôt, un monolithe modulaire déployé en deux processus, web et worker, qui partagent le code, la base et le bucket. Pas de broker : la file asynchrone est une table PostgreSQL, l'outbox.

Pourquoi deux processus et pas de broker ? Un traitement asynchrone (email, OCR) ne doit ni ralentir ni faire échouer une requête HTTP. L'événement s'écrit dans la même transaction que la note ou la décision, puis un second point d'entrée du même code le traite : pas de décision sans événement, pas d'événement sans décision, et aucune nouvelle brique d'infrastructure tant qu'aucun besoin mesuré ne la justifie (ADR-003).

Architecture du code#

Un monolithe modulaire hexagonal léger (ADR-002) : les entrées appellent des cas d'usage, le cœur ne dépend d'aucune infrastructure, les adaptateurs implémentent les ports et la composition assemble le tout.

Où placer le code#

Ce que les outils font respecter
  • ESLint (eslint.config.mjs) : domaine pur ; ni SQL ni accès base dans src/app et src/components ; getPool() réservé à src/lib/db.ts ; withSystemTransaction() réservée au worker, à l'outbox et aux lectures d'avant session ; pas de SQL interpolé ; pas de .only, .skip, .fixme. Plus les règles de SonarQube (eslint-plugin-sonarjs) : bugs, ReDoS, secrets en dur.
  • Test d'architecture (scripts/architecture) : la matrice entière des couches, la garde de chaque méthode de route, et cette page.
  • Les exceptions du code existant (LEGACY_*, LEGACY_EDGES, PUBLIC_ROUTES, eslint-suppressions.json) ne font que raccourcir : jamais d'ajout pour faire passer un contrôle.
Ce qui se passe vraiment

Parcours clés#

Cinq parcours couvrent l'essentiel du code : une requête API, la soumission d'une note, l'outbox, l'OCR et l'identité.

Anatomie d'une requête API#

Exemple : un manager valide une note. Toutes les routes métier suivent le même ordre de vérification : session, rôle, validation, visibilité, règle métier, effet de bord.

  • withApiErrors (src/http) attend toute l'opération, donne un requestId à la requête et transforme toute exception imprévue en 500 INTERNAL_ERROR sans détail ; le détail part au journal JSON du serveur (logError()), sans email ni URL pré-signée.
  • requireRole() est la seule garde : 401 sans session, 403 si le rôle est refusé. proxy.ts ne protège que les pages, jamais /api.
  • La décision verrouille la note (FOR UPDATE) et ne l'écrit que si elle est encore pending : deux décisions simultanées donnent un 200 et un 409, jamais deux 200.

Soumettre une note de frais#

S3 n'est pas transactionnel : l'étape qui peut échouer sans laisser de trace passe en premier. Le reçu est stocké, puis la note et son événement s'écrivent dans une seule transaction (ADR-003 §3 et §4).

Jamais de note sans reçu

Un échec d'upload ne crée aucune ligne ; une contrainte CHECK (receipt_key <> '') l'interdit aussi en base.

Renvoi sans doublon

Le formulaire garde son Idempotency-Key jusqu'au succès : même clé et même contenu rendent la même note (Idempotent-Replayed: true), autre contenu donne 422.

Rien d'orphelin pour longtemps

npm run reconcile:orphan-receipts supprime les objets non référencés de plus de 24 h ; dry-run par défaut. La tâche quotidienne (03:17 UTC, sous expense_worker) est décrite dans ops/cron/expense-io.crontab, à installer sur l'hôte après un premier make reconcile relu.

L'outbox et le worker#

Tout traitement asynchrone du produit passe par une table, outbox_events, et un worker. Le producteur écrit l'événement dans sa propre transaction ; le worker le traite après le commit, au moins une fois. Un échec d'envoi n'annule jamais une décision.

Ajouter un traitement asynchrone
  1. Déclarer le type d'événement, une constante de src/domain ('objet.action').
  2. Le publier par PgEventOutbox dans la transaction métier (celle de withUserScope), avec un payload figé et sans secret.
  3. Écrire le handler dans src/worker : handle(event, client) s'il est court, run(event, signal) idempotent s'il est long, puis le déclarer dans buildHandlers().
  4. Le tester, puis l'ajouter au tableau ci-dessus et à vues/outbox.mmd : npm run check échoue tant que la page ne le cite pas.

Inscription, invitations et session#

Le domaine de l'email ne donne aucun droit (faille S7 corrigée, ADR-001 §3). Les écritures sensibles passent par des fonctions SECURITY DEFINER à surface étroite, et les jetons ne sont stockés qu'en empreinte SHA-256 : le worker les crée au moment d'envoyer l'email, l'outbox ne transporte que des ids.

La connexion est limitée (ADR-001 §4, AUTH-11) : au-delà de 10 échecs pour un même email, ou de 100 pour une même IP, en 15 min, elle est refusée jusqu'à la fin de la fenêtre, même avec le bon mot de passe. /login affiche « Trop de tentatives de connexion », l'appel direct de /api/auth/callback/credentials répond 429 TOO_MANY_LOGIN_ATTEMPTS avec Retry-After. Les compteurs (login_attempts) ne gardent que l'empreinte de l'adresse ; un email inconnu coûte le même bcrypt.compare qu'un mauvais mot de passe.

Session

Auth.js v5, fournisseur Credentials, cookie JWT. Expire après 8 h d'inactivité ; chaque requête repousse l'échéance.

Rôle toujours à jour

Le rôle n'est pas figé dans le jeton : il est relu en base à chaque auth(). Un manager rétrogradé reçoit 403 à la requête suivante, un compte supprimé 401.

Connexion

Un créateur d'entreprise qui n'a pas confirmé son email ne peut pas se connecter (EmailNotVerified) ; il peut redemander le lien depuis /signup/verify.

PostgreSQL

Données et isolation multi-tenant#

Du SQL brut sans ORM, des migrations versionnées, et une isolation entre entreprises portée par la base elle-même.

Montants

numeric(10,2) en base, convertis en number à la frontière ; 99 999 999,99 au plus.

Dates

Chaîne YYYY-MM-DD brute : le parser pg de l'OID 1082 la garde telle quelle, sans fuseau. Ne pas le changer.

Migrations

Nouveau fichier horodaté dans migrations/, avec sa partie down ; jamais d'édition d'une migration existante.

Clés des reçus

receipts/{companyId}/{noteId}.ext et receipts/{companyId}/analyses/{id} : opaques et préfixées par entreprise. Lecture par URL pré-signée de 5 min.

Défense en profondeur#

Une fuite de notes entre entreprises est le pire incident pour un SaaS B2B. L'isolation ne repose donc pas sur un seul contrôle (ADR-001) :

Chaque processus sous son rôle restreint (2-481) L'application se connecte sous expense_app et le worker sous expense_worker, tous deux soumis à la RLS ; le propriétaire expense ne sert qu'aux migrations, au seed et au nettoyage ponctuel. Au démarrage, chaque processus vérifie son rôle (src/lib/dbRole.ts) : un rôle superuser ou BYPASSRLS est refusé en production et signalé en développement. Les WHERE par company_id ou par utilisateur restent, en défense en profondeur, et tout accès aux données d'entreprise passe par withUserScope().
TablePolicies RLS
expense_notespropriétaire : lire et créer ses notes ; manager : lire et trancher celles de ses subordonnés directs de la même entreprise ; RH : celles des managers racines de son entreprise
userslire sa propre ligne et celles de son entreprise ; rattachement (manager_id) par la RH de l'entreprise
invitationsla RH de l'entreprise seulement
outbox_eventsl'application n'a que l'INSERT, dans l'entreprise de l'utilisateur courant ; le worker lit et met à jour les événements de toutes les entreprises
receipt_analysespropriétaire de l'analyse, dans son entreprise

Les policies lisent le contexte que withUserScope() pose au début de chaque transaction (app.current_user_id, puis app.current_company_id et app.current_role lus en base, jamais pris du client). withSystemTransaction(), sans contexte, est réservée par le lint au worker, à l'outbox et aux lectures faites avant toute session, qui n'appellent que des fonctions SECURITY DEFINER.

Rôles PostgreSQL

  • expense : propriétaire des tables ; migrations, seed et nettoyage ponctuel (MIGRATION_DATABASE_URL).
  • expense_app : l'application (DATABASE_URL), NOSUPERUSER NOBYPASSRLS, droits par colonne.
  • expense_worker : le worker et la réconciliation des reçus (WORKER_DATABASE_URL) ; lit et met à jour l'outbox, le reste sous le contexte qu'il pose.
  • expense_definer : NOLOGIN BYPASSRLS, propriétaire des fonctions SECURITY DEFINER.

Les mots de passe des deux rôles restreints sont lus dans .env et posés par npm run migrate:up (scripts/provision-db-roles.mjs).

HTTP

API et contrat#

Le contrat s'écrit d'abord : openapi.yaml décrit chaque opération métier, les types en sont générés, et la CI vérifie que le code et les réponses lui obéissent (ADR-004).

Modifier une opération

  1. Lire openapi.yaml et docs/api/README.md.
  2. Modifier le contrat en premier, puis npm run generate:api.
  3. Importer les types de src/types/api.d.ts (alias dans src/http/dto.ts) ; jamais de DTO local, jamais de fichier généré modifié à la main.
  4. npm run check, puis les E2E concernés.

Conventions

  • URL actuelles, sans /v1 ; listes complètes, sans pagination.
  • Pas de rupture sans décision : sur chaque PR, la CI compare openapi.yaml à celui de main avec oasdiff (make api-breaking en local). Un nouveau code d'erreur n'est qu'un avertissement ; une rupture voulue demande une ADR et le label rupture-contrat.
  • Messages canoniques en anglais avec un code stable ; le front traduit (src/components/apiError.ts).
  • Validation stricte, sans coercition ni valeur par défaut, après la garde et avant toute écriture ou upload.
  • Idempotency-Key facultatif sur la création de note et le lancement d'une analyse.

Routes et gardes, générées depuis le code

Chaque méthode de src/app/**/route.ts et la garde qui l'ouvre. npm run check échoue si une méthode n'a pas de garde ou si ce graphe a dérivé du code.

Erreurs : application/problem+json

Une seule forme d'erreur (RFC 9457), construite par src/http/problem.ts, avec l'en-tête X-Request-Id. Jamais de pile ni de message interne. Le membre error garde les textes historiques pendant la transition ; il est déprécié.

Le schéma Problem d'openapi.yaml porte cette correspondance : un code n'est valide qu'avec son statut. Les réponses des tests E2E étant contrôlées contre le contrat, un FORBIDDEN renvoyé en 400 y échoue.

Pourquoi c'est ainsi

Choix d'architecture#

Chaque choix structurant a été pesé contre des alternatives. Le résumé ci-dessous renvoie à l'ADR qui le décide et le justifie.

Un monolithe modulaire hexagonal léger

Pourquoi. Petite équipe, un seul déploiement et un seul pipeline ; les transactions PostgreSQL restent locales ; les règles se testent sans infrastructure et S3, l'OCR ou l'email se remplacent par un port.

Écarté. Un monolithe simplement nettoyé (le couplage reste) ; des micro-services, disproportionnés pour une poignée de tables, qui changeraient une transaction locale en saga distribuée.

  • ADR-002

L'isolation portée par la base

Pourquoi. Avec la RLS sous un rôle restreint, un WHERE oublié ne fait plus fuir un autre tenant ; c'est une fonction éprouvée de PostgreSQL. Les WHERE restent, en défense en profondeur.

Écarté. Un filtrage centralisé dans le code (reste de la discipline) ; un schéma ou une base par entreprise (exploitation lourde, sans gain de sécurité suffisant).

  • ADR-001 §2

Des invitations, pas le domaine de l'email

Pourquoi. Un attribut non prouvé ne doit pas décider d'une autorisation : s'inscrire le premier sur un domaine permettait de devenir la RH d'une entreprise (S7).

Écarté. Le statu quo ; le domaine avec vérification d'email (la préemption reste possible) ; le domaine vérifié par DNS, gardé en réouverture.

  • ADR-001 §3

Garder Auth.js, rôle relu à chaque requête

Pourquoi. La brique n'était pas en cause : secret dans l'environnement (S5), rôle relu en base et session de 8 h d'inactivité (S9) corrigent ses défauts d'usage sans changer les parcours.

Écarté. Keycloak, Auth0 ou Clerk : parcours de connexion changés, nouvelle dépendance de disponibilité ou de souveraineté.

  • ADR-001 §4

Upload d'abord, puis une seule transaction

Pourquoi. Une transaction SQL ne rend pas S3 transactionnel : l'étape non transactionnelle passe en premier, là où son échec ne laisse rien de visible. Le seul reste possible, un objet orphelin, est réconcilié chaque jour.

Écarté. Un statut intermédiaire (un quatrième statut que les listes et les tests interdisent) ; une compensation après coup (un crash au mauvais moment recrée le bug).

  • ADR-003 §3

Idempotency-Key plutôt que déduplication

Pourquoi. Seule une clé exprime « c'est le même envoi » : deux taxis au même prix le même jour sont légitimes. La clé vit sur la note, sans table ni durée de vie à gérer.

Écarté. Une déduplication sur le contenu ; une clé obligatoire, qui casserait les clients existants.

  • ADR-003 §4

Une outbox transactionnelle et un worker

Pourquoi. Pas de décision sans événement, pas d'événement sans décision ; un échec SMTP n'annule rien ; livraison au moins une fois, relances et DLQ. Un seul mécanisme sert aux emails et à l'OCR, et servira à l'IA.

Écarté. L'envoi dans la route (la décision dépendrait de SMTP) ; after() de Next.js (perdu au moindre crash) ; un broker, sans besoin mesuré.

  • ADR-003 §5

Un OCR borné, isolé, puis asynchrone

Pourquoi. Le coût suit les pixels, pas les octets : on borne octets, pixels, concurrence et durée. Le moteur tourne dans un processus jetable, qu'on peut tuer à l'échéance ; l'interface passe par 202 et polling.

Écarté. L'OCR illimité dans la requête ; un worker Tesseract gardé chaud, une optimisation jamais mesurée.

  • ADR-003 §1 et §2
  • docs/ocr.md

Le contrat d'abord, des erreurs normalisées

Pourquoi. Un contrat explicite, lisible par les humains et les agents ; des types générés partagés par le serveur et le front ; des codes stables que le front traduit, pour des utilisateurs internationaux.

Écarté. Une documentation tirée des handlers ; un format d'erreur maison ; un préfixe /v1 et une pagination sans besoin.

  • ADR-004

SQL brut et migrations SQL

Pourquoi. Convention du projet : pas d'ORM. Policies RLS, fonctions SECURITY DEFINER et contraintes s'écrivent de toute façon en SQL ; les requêtes restent paramétrées ($1, $2), un tri passe par une liste blanche.

En pratique. node-pg-migrate, une migration horodatée par changement, avec sa partie down.

  • CLAUDE.md

Un harnais à plusieurs étages

Pourquoi. Protéger les E2E des correcteurs à chaque PR, distinguer une régression d'un changement voulu, et rendre les règles exécutables, y compris pour une IA qui écrit vite.

Écarté. Des hooks git seuls (contournables) ; un runner auto-hébergé sur un dépôt public ; un seuil de couverture bloquant.

  • ADR-005

KISS sur l'infrastructure

Pourquoi. Aucune nouvelle brique sans besoin mesuré : PostgreSQL sert de base, de file et de verrou des moteurs OCR. L'international passera par une instance par région, sans base répliquée.

Réouverture. Un volume d'outbox que le polling n'absorbe plus, une IA externe, un workflow entre régions.

  • ADR-001
  • ADR-003
Décisions

Les ADR#

Une ADR (Architecture Decision Record) consigne une décision structurante : contexte, options, décision, conséquences. Seules les ADR au statut « Acceptée » font foi ; un test E2E ne change que si l'une d'elles décide le changement de comportement.

ADR-001Acceptée

Stratégie d'isolation multi-tenant

Amalraj Soupramanien (WS1, sécurité) · acceptée le 20/10/2026, précisée le 23/10

Décide

  • RLS effective sous un rôle non superuser, WHERE conservés, règles d'action dans un module de permissions du monolithe.
  • Le domaine de l'email ne donne aucun droit : invitations de la RH, vérification d'email du créateur, création atomique de l'entreprise et de sa RH (S7).
  • Garder Auth.js : secret dans l'environnement (S5), rôle relu en base et session de 8 h (S9).
  • Preuves par la suite E2E : ISO-04 à 09, SIGNUP-08, AUTH-10 ; une instance par région pour l'international.

Journal et métriques#

Serveur et worker écrivent une ligne JSON par événement, sans email, jeton ni URL pré-signée (ADR-005 §5). Une réponse d'erreur porte son requestId (corps et X-Request-Id), repris dans la ligne http.error. Deux lignes servent de métriques à un collecteur de logs (ADR-003, mise à jour du 27/10) :

LigneMétriqueÉcrite par
ocr.requestocr_requests_total{outcome} : found, empty, rejected, failed, timeout, overloaded, avec durationMs et requestIdle serveur, à chaque suggestion OCR
outbox.statsévénements pending et dead, âge du plus ancien en attente, au total et par type (OBS-01)le worker, chaque minute
Avant de déclarer une tâche terminée npm run check passe. Si le changement touche src/app, src/lib, migrations/ ou scripts/, les E2E concernés passent aussi, ou toute la suite. Un bug corrigé vient avec un test vu rouge avant la correction et vert après. Dire explicitement ce qui n'a pas été lancé.

Déploiement et exploitation#

Ce que la production exige, l'ordre d'une mise en production et ce qu'on surveille ensuite. Les processus sont décrits dans la vue d'ensemble, les variables dans Démarrer : cette section n'y revient pas.

Aucun hébergement n'est choisi Le dépôt ne contient pas d'image de conteneur de l'application et ne vise aucune plateforme. Le tableau ci-dessous décrit des exigences, pas une infrastructure existante.

Mettre une version en production#

  1. Le commit est sur main, donc sa CI est verte : check et e2e sont requis pour fusionner (harnais).
  2. npm run migrate:up sous le propriétaire (MIGRATION_DATABASE_URL) : applique les migrations, puis pose les mots de passe des rôles restreints (scripts/provision-db-roles.mjs).
  3. npm run ensure-bucket si le bucket est nouveau.
  4. Démarrer le web, puis le worker. En production, chacun refuse de démarrer sous un rôle superuser ou BYPASSRLS ; le web refuse aussi un AUTH_SECRET absent, court ou d'exemple, et le worker une configuration sans SMTP_HOST ni APP_URL (variables).
  5. Une seule fois : installer la tâche de ops/cron/, après un premier passage à blanc dont le rapport a été relu.

Retour arrière : revert du commit et redéploiement (ADR-006). Une migration ne s'annule que par son down (npm run migrate:down) ; une migration déjà appliquée ne s'édite jamais.

Plusieurs régions#

Une instance complète par région (web, worker, base, bucket), une entreprise rattachée à une seule région, sans réplication entre régions (ADR-001, ADR-002). Le sujet se rouvre si un manager doit valider des notes stockées dans plusieurs régions : c'est le cas où le théorème CAP impose de choisir entre cohérence et disponibilité.

Non décidé L'hébergeur, l'image de conteneur, la sauvegarde et la restauration de la base, les alertes (les métriques existent, pas les seuils ni les destinataires), un outil de relance de la DLQ et les traces distribuées. Repris dans la dette connue.
Lucidité

Dette connue et chantiers ouverts#

À ne pas reproduire, et à ne pas « corriger au passage » dans une PR sans rapport : chaque point a son ticket ou son ADR.

architecture Règle d'accès à deux endroits

Plus aucune route ne fait de SQL (ADR-006). Mais « qui voit quoi » vit dans le domaine pour une note (decideExpenseNote, canViewReceipt) et dans le WHERE des listes (PostgresExpenseNoteListRepository) : les faire évoluer ensemble.

exploitation Tâches et observabilité

Nettoyage unique des notes sans reçu à exécuter puis valider (npm run clean:notes-without-receipt) ; tâche quotidienne de ops/cron/ à installer une fois un environnement déployé. Les métriques sont des lignes de journal (ocr.request, outbox.stats) : sans collecteur de logs, ni tableau de bord ni alerte ; pas de traces distribuées (ADR-005 §5). Hébergeur, image de conteneur, sauvegardes de la base et relance de la DLQ ne sont pas décidés (déploiement).

qualité Constats figés

Les constats SonarJS du code existant sont figés dans eslint-suppressions.json, qui ne fait que raccourcir ; CODEOWNERS n'est pas encore en place.

Constats détaillés : docs/audit/ (sécurité S1 à S9, architecture A1 à A3, API Q1 à Q3 et B1 à B16).

Contribuer#

Un changement, une branche, une petite PR relue par un pair.

  1. Partir de main à jourgit pull, puis npm install si package.json a changé.
  2. Une branche par changementNommée avec le ticket Linear : fix/2-471-correctifs-securite.
  3. Lire avant d'écrireCLAUDE.md, les ADR acceptées concernées, le contrat si l'API change, les fichiers voisins.
  4. Domaine d'abordRègle et test, puis port et adaptateur, route fine, interface.
  5. Mettre à jour cette pageDans la même PR (comment).
  6. Vérifiernpm run check, puis les E2E concernés.
  7. Ouvrir la PRgh pr create --repo 2-MORGAN/expense-io --base main, en remplissant le modèle ; commits conventionnels (feat(ocr): …, fix(api): …).
  8. FusionnerPar squash, une fois check et e2e verts et la PR relue.

Jamais

  • --no-verify, un push sur main, un force-push.
  • Modifier, désactiver ou supprimer un test E2E pour faire passer la CI.
  • Ajouter une entrée aux listes LEGACY_*, à LEGACY_EDGES, à PUBLIC_ROUTES ; eslint --suppress-all.
  • Un eslint-disable sans commentaire qui le justifie.
  • Éditer une migration existante, concaténer du SQL, faire confiance à un id venu du client.
  • Un secret dans le code, un message interne ou une pile dans une réponse.
  • Une dépendance npm sans justification dans la PR.

La recopie

npm run generate:architecture régénère les graphes et recopie graphes et vues dans cette page, entre leurs marqueurs. Mêmes sources, même page, octet pour octet.

npm run check (scripts/architecture/architecture.test.ts) échoue si la page a dérivé de ses schémas, si un schéma n'y a pas sa place ou si un marqueur n'a plus de schéma, si une ADR de docs/adr n'a pas sa fiche, si une table des migrations manque au schéma des données (ou s'il y en a une de trop), si un type d'événement de l'outbox n'est pas cité, ou si un script externe est chargé sans empreinte SRI. Le texte, lui, ne se vérifie pas : d'où la règle suivante.

Ajouter un schéma Créer docs/architecture/vues/nom.mmd (en-tête de commentaire comme les autres), placer dans cette page une figure avec les marqueurs <!-- début : vues/nom.mmd --> et <!-- fin : vues/nom.mmd -->, puis npm run generate:architecture. Pour l'essayer : mermaid.live, ou cette page ouverte dans un navigateur. Mermaid est chargé depuis jsDelivr, en version fixe, avec des identifiants déterministes.
Vocabulaire

Glossaire#

NDF
Note de frais : montant, date, description et reçu, au statut pending, approved ou rejected.
Tenant
Une entreprise cliente (companies). Aucune donnée ne doit passer d'un tenant à l'autre.
Manager racine
Manager sans manager (manager_id NULL) : la RH de son entreprise tranche ses notes.
RLS
Row Level Security : policies PostgreSQL qui filtrent les lignes selon le contexte de la transaction.
withUserScope()
Ouvre une transaction et pose le contexte lu par les policies (utilisateur, entreprise, rôle). Seul accès aux données d'entreprise.
SECURITY DEFINER
Fonction SQL exécutée avec les droits de son propriétaire, pour une opération étroite et contrôlée.
Port, adaptateur
Interface dont le cœur dépend, et son implémentation technique (PostgreSQL, S3, SMTP, Tesseract).
Composition
src/composition : l'endroit unique où l'on assemble cas d'usage et adaptateurs.
Outbox
Table outbox_events où un événement s'écrit dans la transaction métier, avant d'être traité par le worker.
Bail, DLQ
Durée (5 min) pendant laquelle un worker garde un événement pris en charge ; un événement dead a épuisé ses essais (dead letter queue).
Idempotency-Key
UUID envoyé par le client pour qu'un renvoi rende le même résultat au lieu d'un doublon.
problem+json
Format d'erreur de la RFC 9457 : type, title, status, detail, plus code et requestId.
URL pré-signée
Lien S3 temporaire (5 min) vers un reçu, délivré après le contrôle d'autorisation.
ID de test
Identifiant d'un scénario E2E (NDF-06, ISO-07…), listé dans docs/tests/E2E.md et lançable par -g.
ADR
Architecture Decision Record : décision structurante écrite, qui ne fait foi qu'au statut « Acceptée ».
