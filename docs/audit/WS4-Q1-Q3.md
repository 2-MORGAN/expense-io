# WS4 — Audit API : Q1 à Q3 et constats complémentaires

Audit du **10 octobre 2026**, commit `4fad1d3c4683082422d67ae72979a2c1f08e3ff1`.
Périmètre : tous les handlers de `src/app/api`, leurs dépendances auth/SQL/S3/OCR, et l'inscription serveur dans la mesure où elle attribue les droits API. Aucun audit de l'interface ni refactoring effectué.

**Résultat :** Q1 confirmée avec nuance (codes incohérents, mais enveloppe métier commune) ; Q2 confirmée dans le dépôt ; Q3 confirmée pour la sérialisation, les gardes d'accès et les décisions, avec moins de duplication des validations de champs qu'attendu.

Méthode : lecture exhaustive des **14 fichiers `route.ts`**, comptage et comparaison des clones, vérifications isolées de handlers avec auth/DB/S3 simulés, lecture des implémentations Next.js/Auth.js installées. **Pas de tests HTTP de bout en bout ni d'exploitation sur PostgreSQL/S3 réels** ; les dépendances simulées prouvent le comportement du handler, pas celui de l'infrastructure. Les remarques de `CLAUDE.md` ont été revérifiées dans le code.

Priorisation : **C4 critique** (compromission/isolation), **C3 élevée** (intégrité, fuite, indisponibilité), **C2 modérée** (fiabilité, maintenance), **C1 faible**. Effort estimé, correction ciblée et vérification incluses : **S ≤ 1 j**, **M = 2–3 j**, **L = 4–5 j**. `C × E` désigne la paire criticité–effort, pas un produit numérique ; estimations non additives lorsque les correctifs se recouvrent.

## 1. Inventaire des routes

Préfixe de toutes les URL : `/api`. Chaque chemin correspond à `src/app/api/<chemin>/route.ts` ; `:id` correspond au dossier `[id]`. Les identifiants ci-dessous servent aussi de références de fichier, suivis des lignes.

`A` = utilisateur connecté, quel que soit son rôle ; `M` = rôle exact `manager` ; `H` = rôle exact `hr_admin` (pas de hiérarchie implicite des rôles).

| Réf. | Méthode et chemin | Accès réellement vérifié | Succès | Erreurs prévues dans le handler |
|---|---|---|---|---|
| EN | GET `/expense-notes` | A ; notes de soi | 200, `Note[]` | 401 ; 500† |

| AUTH | GET, POST `/auth/[...nextauth]` | Public/session selon action ; Credentials pour se connecter ; CSRF Auth.js sur les POST concernés | 200 JSON/HTML ; 302 redirection | 400, 403, 500 ; erreurs également signalées par redirection 302 ou JSON `{url}` en 200 |

**Comptage : 14 opérations métier dans 13 fichiers + 1 fichier Auth.js exportant GET/POST = 16 exports HTTP dans 14 fichiers.** Le catch-all Auth.js distribue plusieurs sous-actions, sans les compter comme des fichiers supplémentaires.

- `Note` : `id, userId, amount` (number), `expenseDate, description, receiptKey, status, createdAt` ; `User` : `id, name, email, role, managerId`.
- EN POST accepte un `multipart/form-data` : `amount, expenseDate, description, receipt` ; OCR accepte `receipt` ; UM attend du JSON `{managerId: UUID | null}` mais ne valide pas réellement ce schéma. EN GET accepte `sort`, directement traité comme SQL.
- † **7 handlers** font `return withUserScope(...)` sans `await` : les rejets asynchrones DB/sérialisation/commit échappent au `catch`. Le serveur prend alors en charge l'erreur ; le format JSON applicatif du 500 n'est plus garanti. Les autres exceptions capturées produisent `{error, stack?}`.
- Next.js ajoute `OPTIONS` (204, `Allow`) à chaque fichier et `HEAD` via GET lorsqu'il existe ; méthodes non implémentées : 405 sans enveloppe JSON métier. Vérifié dans `node_modules/next/dist/server/route-modules/app-route/helpers/auto-implement-methods.js:13–69`.
- AUTH : GET `session`, `csrf`, `providers` renvoient du JSON ; GET `signin` redirige vers `/login`, GET `signout` affiche une page ; POST `callback/credentials`, `signin`, `signout`, `session` sont distribués par Auth.js. GET `error` peut répondre 200/403/500 HTML ; `verify-request` et `webauthn-options` existent dans le distributeur mais aucun fournisseur email/WebAuthn n'est configuré. Chemin/action malformé : 400. Le header `X-Auth-Return-Redirect` peut transformer une redirection en 200 `{url}`. Sources : `src/lib/auth.ts:10–43`, `node_modules/@auth/core/src/lib/index.ts:41–96`, `node_modules/@auth/core/src/index.ts:101–200`, `node_modules/@auth/core/src/lib/utils/web.ts:74–95`, `node_modules/@auth/core/src/lib/pages/error.tsx:27–76`. **Ce protocole de bibliothèque est distinct du contrat métier** ; ses variations ne sont pas, seules, un défaut.

## 2. Q1 — Codes et formats d'erreur

| ID | Constat, emplacement et mesure | Impact | C × E / correction ciblée |
|---|---|---|---|
| Q1.1 | **401/403 confondus.** 4 handlers manager répondent 401 aussi pour un mauvais rôle (`ML:20–23`, `MA/MJ:7–10`, `MR:8–11`) ; 6 handlers RH répondent 403 aussi sans session (`HL:20–23`, `HA/HJ:7–10`, `HR:8–11`, `UL/UM:7–10`). Les 4 handlers personnels répondent 401 sans session. | Le client ne distingue pas « se connecter » de « accès interdit » ; comportement différent selon l'espace. | **C2 × S** — garde commune : 401 sans session, 403 si rôle refusé. |
| Q1.2 | **Enveloppe partiellement homogène, non structurée.** Les 14 handlers utilisent `{error: string}` pour leurs refus explicites et le même helper pour les exceptions ; ce dernier ajoute le message interne et `stack` (`src/lib/errors.ts:1–5`). Aucun code d'erreur applicatif stable ni détail par champ ; messages français et anglais. EN utilise 400 pour champs/type/taille, UM utilise 409 pour manager invalide (`EN:79–85`, `UM:33,44`). | Parsing dépendant du texte, traduction difficile, erreurs peu exploitables ; fuite technique détaillée en B4. Le 409 d'UM n'est pas intrinsèquement faux, mais sa sémantique n'est pas documentée. | **C2 × M** — catalogue et schéma d'erreur communs ; formaliser validation/conflit/type/taille. |
| Q1.3 | **Gestionnaire d'erreur contourné dans 7/14 handlers.** `EN:44–52`, `ML:25–36`, `HL:25–37`, `MA/MJ:13–45`, `HA/HJ:13–46` retournent une promesse sans l'attendre dans le `try`. | Une même erreur SQL est renvoyée par le framework ici, par `{error, stack}` ailleurs ; `.json()` côté client peut échouer. | **C3 × S** — attendre la promesse dans le `try` ou adopter un wrapper qui capture les rejets. |

**Nuance essentielle :** il n'y a pas une multitude de formats d'erreurs métier différents d'une route à l'autre. La variation démontrée concerne surtout les **codes d'authentification**, les **exceptions techniques**, et le protocole Auth.js séparé. Le helper commun constitue déjà un point de mutualisation, mais il est dangereux et partiellement contourné.

## 6. Vérifications et ordre de traitement

Les vérifications isolées ont confirmé : différence 401/403 ; rejet DB échappant au catch d'EN GET versus 500 avec stack sur MR ; JSON malformé d'UM provoquant un UPDATE avec `manager_id = null` et 200 ; recherche manager sans entreprise ; concaténation effective du tri ; signature du reçu manager sur le seul id ; transmission de `12abc` sous forme de `12` et d'une date invalide à la DB. **Le 201 simulé de ce dernier cas ne signifie pas que PostgreSQL accepte une date invalide.** Les chiffres de duplication et les deux paires approve/reject ont été vérifiés par comparaison de source.

Contrôles du dépôt : **`npm run lint` et `npm run typecheck` réussis**. Aucun test API permanent ajouté pour cet audit documentaire ; aucune infrastructure démarrée et aucune donnée modifiée.

1. **Sécuriser les accès** : B1–B6 et B12 ; tester explicitement l'isolation interentreprises et la révocation.
2. **Préserver l'intégrité** : B7–B10, B13 ; uniformiser immédiatement la capture des erreurs et les codes (Q1).
3. **Stabiliser le contrat avant refonte** : Q2, puis supprimer les duplications Q3 et isoler les responsabilités (B15), avec tests de non-régression.

Cet audit identifie les corrections attendues ; il ne définit pas encore l'architecture cible complète.
